# DSpark drafter: what the official recipe says, and what our row economics allow

Researched 2026-11-08 for the drafter teammate (task-3). Every external fact has a URL; the arithmetic is
mine and marked.

## 1. The official training code exists: deepseek-ai/DeepSpec (MIT)

https://github.com/deepseek-ai/DeepSpec — "a full-stack codebase for training and evaluating draft models
for speculative decoding". Contains data prep (download/split prompts, regenerate target answers, build the
target cache), draft-model implementations, training, and eval over gsm8k / math500 / aime25 / humaneval /
mbpp / livecodebench / mt-bench / alpaca / arena-hard-v2.

Algorithms: DSpark (arXiv 2607.05147), DFlash (2602.06036), Eagle3. Draft model implementations ship for
**Qwen3 and Gemma4 only** — a DeepSeek-V4.1 target needs a new `deepspec/modeling/dspark/deepseek_v41/`
(the head is the same: backbone + markov head + confidence head; the backbone class is V4.1-specific).

The DSpark training config (`config/dspark/dspark_qwen3_4b.py`, https://github.com/deepseek-ai/DeepSpec/
blob/main/config/dspark/dspark_qwen3_4b.py) — this is DeepSeek's own recipe, the one the paper used:

```
block_size=7, num_draft_layers=5, target_layer_ids=[1,9,17,25,33], num_anchors=512
markov_rank=256, markov_head_type='vanilla'
confidence_head_alpha=1.0, confidence_head_with_markov=True
loss_decay_gamma=4.0, ce_loss_alpha=0.1, l1_loss_alpha=0.9
lr=6e-4, warmup_ratio=0.04, bf16, global_batch_size=512, num_train_epochs=10,
sharding_strategy='no_shard' (DDP), torch_compile=True, 8 GPUs
data: max_length=4096, open-perfectblend regenerated by the target model, non-thinking
```

Two things to note:

- **The objective is already a distribution-matching (TV) loss, not CE.** `deepspec/modeling/dspark/loss.py`
  computes `accept_rate = 1 - 0.5*sum|p_draft - p_target|` and the L1 term is
  `sum|p_draft - p_target|` weighted at 0.9 against 0.1 for CE. So the "Ltv" of the paper is this term.
  Consequence: TVP's headline "+9.8% acceptance length over CE" is **not** the gain available to us — the
  shipped recipe is already TV-heavy; TVP's fairer comparison is its "+6.2 to 12.9% over the public
  DFlash2 training recipes" (arXiv 2611.00588 abstract), and even that is a different drafter family.
- **The released drafters are trained on non-thinking data**, and the README warns: "For domain-specific
  use, fine-tune the draft model again for better results, especially if the target model is expected to
  run in thinking mode." That is our exact case (thinking at max effort). It is a hypothesis for our
  alpha = 0.77 on thinking prose, not a proof: the checkpoint's MTP head is DeepSeek's, trained on their
  own data, not on open-perfectblend.

Cost driver, not the GPUs: the **target cache** (regenerate the dataset with the target model). README
warns it is "roughly 38 TB for the default Qwen3-4B setting". On our 4x RTX PRO 6000 box the target decodes
at ~370 tok/s aggregate, so regenerating even 1B tokens is ~31 days of wall clock — the cache generation,
not the drafter training, decides whether retraining is affordable. Cheaper sources: the model's own
thinking-mode outputs from production traffic (free, in distribution, and exactly the workload we serve).

## 2. What our checkpoint's drafter actually is

From `deepseek-ai/DeepSeek-V4.1-Flash-1017/config.json` (text_config):

```
num_nextn_predict_layers = 3
dspark_block_size = 5            <- the trained block; k>5 is out of distribution
dspark_target_layer_ids = [37, 38, 39]
dspark_markov_rank = 256
dspark_n_routed_experts = 128, dspark_num_experts_per_tok = 3
dspark_noise_token_id = 128799
```

No `dspark_draft_topk` key: the split-vocabulary top-k draft path in the vLLM DSpark speculator
(`vllm/v1/worker/gpu/spec_decode/dspark/speculator.py:78-79, 217-223`) is unset.

Note how different it is from DeepSpec's defaults: 3 draft layers against 5, hidden states from the last
three layers rather than every 8th, block 5 against 7. So "run the official recipe" means re-deriving the
V4.1 draft architecture in DeepSpec, not reusing a config.

## 3. The row economics: alpha first, then a longer trained block

A verified row costs ~0.4-0.5 ms of step time on this stack (each row adds ~3 distinct experts x 4.7 MB
per rank x 40 layers; the k-sweep agrees: k5 = 110 steps/s at 3.45 accepted, k7 = 97 at 3.55). So a row
pays only if it adds more than `A * dT/T` = 3.45 x 0.5/8.77 = **0.2 accepted tokens**.

The uniform-alpha model `A = 1 + sum_{i=1..k} alpha^i` fits our in-block data exactly (alpha 0.77, k=5 ->
3.44 predicted vs 3.45 measured) and fails beyond the trained block (k=7: 3.81 predicted, 3.55 measured -
positions 6-7 are out of the block the head was trained for). So the model is valid only up to the trained
block size, and that is the key: **a longer block makes the row budget usable.**

tok/s on the uniform-alpha model, step = 8.77 + 0.45*(k-5) ms (my arithmetic; row cost is an estimate):

| alpha | k=5 | k=6 | k=7 | k=8 | k=9 | best |
|---:|---:|---:|---:|---:|---:|---|
| 0.77 (today) | 392 | 396 | 394 | 389 | 381 | k=6, 396 |
| 0.80 | 421 | 429 | 430 | 428 | 422 | k=7, 430 |
| 0.85 | 473 | 491 | 502 | 506 | 507 | k=9, 507 |
| 0.88 | 509 | 534 | 552 | 563 | 569 | k=9, 569 |
| 0.90 | 534 | 566 | 589 | 605 | 616 | k=9, 616 |
| 0.93 | 575 | 617 | 651 | 677 | 697 | k=9, 697 |

Three regimes:

1. **At today's alpha the extra rows are worthless**: 392 at k=5 vs 396 at k=6 is inside the noise, and the
   measured k=6/k=7 are worse because those positions are untrained.
2. **Alpha alone, inside block 5, caps at ~534 tok/s** (alpha 0.90, k=5). Not 600.
3. **Alpha 0.88-0.90 plus a trained block of 8-9 reaches 563-616.** That is the only route to 600 the row
   budget allows, and it is one training run, not two: DeepSpec's configs take `block_size` as a
   hyperparameter (its released DSpark checkpoints are block 7; the paper trains block 16 for its scaling
   study).

So the drafter target is: **alpha 0.88-0.90 on thinking prose, with the block trained at 8 or 9.** On top of
the ~9% step-time work in LEADS.md L4-L9 (row cost 0.45 -> 0.41 ms), alpha 0.90 + block 9 lands ~677 tok/s.

Caveats: uniform alpha is an idealisation (real curves decay), the row cost is a fitted estimate, and
distinct experts saturate (10 rows x top-6 = 60 slots against 384 experts, so the marginal row should get
cheaper, not dearer - if anything the table is conservative at high k).

## 4. Negative results already on record

- `Avifenesh/DeepSeek-V4.1-Flash-DSpark-drafter-ft` (2026-10-29, fp8, 7.93 GB): "A fine-tune of the three
  MTP layers ... trained on the served model's own outputs. The gain is small: more accepted draft tokens
  in non-thinking mode, **about flat in thinking mode at temperature 1**." So a plain fine-tune on the
  model's own outputs did not move thinking acceptance. Whatever we do must change something the naive
  fine-tune does not: the loss (TVP), the data (thinking-mode agent traces with tool calls), or capacity.
- `SubconsciousDev` retrained drafter: measured by us at 1-3% fewer accepted tokens on reasoning, 4% on
  code, 2-6% slower decode.
- PCTree (arXiv 2608.02123, training-free tree over the Markov head) buys its acceptance with verify
  nodes at 0.037 accepted/node on Qwen3-4B GSM8K, against our 0.2/node bar: not worth it here.

## 5. Papers to read before writing training code

- arXiv 2607.05147 (DSpark): the confidence head, the position weighting `exp(-(k-1)/gamma)`, and the
  acceptance-vs-block-size curves (their Fig. 4: accepted length 3.2 -> 6.4 as block 4 -> 16 on code).
- arXiv 2611.00588 (TVP): loss family parameterised by a power that anneals 0 -> 1 between coverage and
  acceptance objectives; "+9.8% acceptance length over CE when fine-tuning".
- arXiv 2608.02123 (PCTree): what the Markov head can and cannot do without retraining.

## 6. Calibration: what accepted length looks like at temperature 1.0 (DSpark paper, Table 1)

The DSpark paper's benchmarks all use "standard speculative decoding ... with the sampling temperature set
to 1.0" (arXiv 2607.05147v1, Sec. 4.2), so its accepted lengths are directly comparable to our 3.45:

| target | drafter | Math | Code | Chat |
|---|---|---:|---:|---:|
| Qwen3-4B | DSpark | 6.11 / 5.70 / 4.89 (GSM8K / MATH / AIME25) | 5.13 / 5.38 / 4.86 (MBPP / HumanEval / LCB) | 3.64 / 3.54 / 3.29 (MT-Bench / Alpaca / Arena-Hard) |
| Qwen3-8B | DSpark | 6.17 / 5.78 / 5.01 | 5.16 / 5.52 / 5.17 | 3.72 / 3.58 / 3.21 |
| Qwen3-14B | DSpark | 6.21 / 5.74 / 4.94 | 5.26 / 5.43 / 5.02 | 3.70 / 3.58 / 3.13 |

The paper says it directly: "the accepted length is naturally higher on structured tasks (e.g., 5.57 on math
and 5.12 on code for Qwen3-4B) than on open-ended chat (3.49)".

**Our 3.45 on thinking prose at T=1.0 is exactly the published open-ended-chat level.** So the drafter is
not broken; prose at T=1.0 is the hard case, and the +14% alpha target (0.77 -> 0.88) is asking for
code-level acceptance on prose. The one thing that makes it plausible is that the published drafters are
out-of-domain for our workload (DeepSpec's released checkpoints are trained on open-perfectblend
non-thinking data; the README warns to fine-tune for thinking mode), while ours would be trained on the
served model's own thinking traces.

Position-1 conditional acceptance from their Figure 2 (Qwen3-4B): DFlash 0.88 Math / 0.72 Chat, Eagle3
0.81 / 0.53. Ours is unknown; that is what the per-position metric (`bench/thinkbench.py`) would give, and it
separates "capacity at position 1" from "decay at positions 2-5".
